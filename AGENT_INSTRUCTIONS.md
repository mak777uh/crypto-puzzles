# Инструкции для агентов, работающих с каталогом загадок

Этот каталог — живая база знаний. Любой агент, который исследует пазл или продвигает решение,
**обязан** обновлять данные там, где они лежат, чтобы знания не потерялись и не дублировались.

## Обязательное правило (главный протокол)
1. Перед началом работы прочитать этот файл и `MASTER_CATALOG.md` (хотя бы relevant часть).
2. **Журнал пазла `LOG.md` (обязательно).** Каждый агент, работающий над пазлом, ведёт в папке пазла
   хронологический журнал `puzzles/<slug>/LOG.md`:
   - при первом заходе по пазлу — **представиться** (имя агента / модель / среда сессии);
   - далее по датам фиксировать **всё значимое**: что делал, что нашёл (включая **отрицательные результаты**),
     какие скрипты/файлы создал или использовал, проверки балансов, найденные ссылки;
   - ничего значимого не должно оставаться только в чате или рабочем воркспейсе — папка пазла должна быть самодостаточной;
   - записи **добавляются в конец**, старое не затирается. Формат — ниже.
3. Если найдена значимая информация (подсказка, вывод, декод, проверка баланса, новый источник/ссылка, гипотеза, отрицательный результат):
   - полная запись — в `puzzles/<slug>/LOG.md`;
   - если это **прорыв или меняет картину пазла** — краткое обновление `puzzles/<slug>/README.md` (append, не затирая старое; дата и источник);
   - если влияет на глобальную картину (балансы/движения, решённые, мёртвые, статус) — обновить `MASTER_CATALOG.md` и, при необходимости, `WAKE_QUEUE.md`.
4. **Код хранится в папке пазла.** Скрипты, оракулы, генераторы, json-дампы, логи прогонов складывать
   в `puzzles/<slug>/tools/` (код) и `puzzles/<slug>/data/` (данные/результаты) — не оставлять только в рабочем воркспейсе.
   (Если код исторически лежит в `data/` — допустимо, главное чтобы он был в папке пазла.)
5. Если решена часть пазла или весь пазл — сначала sweep (снять приз), потом опубликовать (write-up) и зафиксировать:
   - метод (краткая цепочка),
   - доказательства (txid, блок, адрес, расчёты),
   - что именно было «ключом» (инсайт),
   - ссылки на опубликованные детали.
6. Любое изменение делать с датой (YYYY-MM-DD), именем агента (если есть), и ссылками. Краткий лог изменений тоже можно вести в `WAKE_QUEUE.md`.
7. Не дублировать большие тексты в `MASTER_CATALOG.md` — расширяйте папку пазла, а в каталог добавляйте краткую отсылку.
8. Источники (URL) обязательны. Без ссылки фиксация считается неполной.
9. **GitHub-интейк — обязательный первый шлюз (правило Ильи от 18.10.2026).** Агент, который берёт в
   работу базу или отдельную загадку, **сначала** собирает на GitHub всю информацию по ней из
   репозиториев. Пока шлюз не выполнен и не зафиксирован в `puzzles/<slug>/LOG.md` (оформленный негатив
   «репо не найдено, проверено по N запросам» — тоже выполнение), агент **не выставляет строку в
   `PROPOSALS.md` и не запускает проверочный прогон**. Полный порядок, команды и лимиты — раздел
   «GitHub-интейк — обязательный первый шлюз» ниже.

## Главный принцип разделения (что куда писать)
- `puzzles/<slug>/README.md` — **только прорывы и важное**: актуальный статус, ключевые выводы, зацепки, где что лежит. Читается первым, должен оставаться коротким и точным.
- `puzzles/<slug>/LOG.md` — **полная хроника**: каждая сессия агента, все значимые шаги и результаты (в т.ч. отрицательные), самопредставление агентов. По датам, новые записи в конец.
- `puzzles/<slug>/tools/`, `puzzles/<slug>/data/` — код и данные/артефакты (скрипты, json, логи, дампы).

## Формат журнала `puzzles/<slug>/LOG.md`
Новые записи добавляются в конец файла:
```
## YYYY-MM-DD, HH:MM — <агент> (<модель/среда>)
- Делал: ...
- Результат: ... (включая отрицательные результаты!)
- Артефакты: tools/xxx.py, data/yyy.json
- Ссылки/доказательства: ...
```

## Формат дополнения в `puzzles/<slug>/README.md`
Добавляйте секцию:
```
## Обновление (YYYY-MM-DD, <агент>)
- Тип: подсказка / прогресс / баланс / отрицательный результат / решение
- Суть: ...
- Источник: <url>
- Проверено: да/нет (каким способом)
- Влияние на оценку: ...
- Подробности и хроника: см. LOG.md
```

## Оперативные правила приоритета (установлены Ильёй 17.10.2026)
1. **Приоритет — быстро добыть деньги.** Сначала цели, где уже известен ключ/механика и остался один шаг; потом крупные призы с математическим/инсайт-углом.
2. **Приоритет он-чейн лидам.** Балансы, старые подсказки в транзакциях, публичные ключи, контракты — раньше, чем форумы и догадки.
3. **Перебор — на GPU или CPU, не дольше 15 минут на прогон.** Жёсткий потолок; длиннее — только с явного письменного ОК Ильи и с обоснованием (не «на всякий случай»). Пополнение/продление прогона = новый прогон, тот же потолок.
4. **Перебор — только по инсайт-оси.** Сначала из текста/видео/метаданных выводится конкретная гипотеза/модель (какие слова, какой порядок/трансформация, какой диапазон) — и перебирается ТОЛЬКО суженная ею ось. Слепой перебор «на авось» без инсайта запрещён на любой технике. Гипотеза и ось фиксируются в LOG.md до запуска прогона.
5. **Никаких трат и трансляций без ОК Ильи:** платные подсказки, депозиты, комиссии, письма авторам/решателям, публикации. Подготовить черновик/транзакцию и запросить разрешение.
6. **Ключи/сиды — только в `.secret/` (chmod 600)**, никогда в открытом виде в README/LOG/чате; передавать только лично Илье.
7. **Регулярный отчёт:** каждый проход — краткий отчёт в `WAKE_QUEUE.md` + обновление папки пазла; значимое — в LOG.md, прорывы — в README, глобальное — в MASTER_CATALOG.
8. **Новые загадки** — сразу заводить папку `puzzles/<slug>/` (README + LOG), добавлять в индекс и каталог.

## Что нельзя делать
- Затирать чужую проделанную работу — только дополнять.
- Публиковать seed/PRIVATE KEY до снятия приза.
- Удалять источники и старые гипотезы (перечёркивать/помечать устаревшими вместо удаления).
- Заменять факты выдумкой.

## Оркестрация (самобудильник)
- Автономный цикл описан в `WAKE_QUEUE.md`: каждый проход читает очередь, выполняет задачи, обновляет данные (по этому протоколу), ставит новый таймер.
- Детальный отчёт прохода — отдельный файл `reports/ГГГГ-ММ-ДД_ЧЧММ_<агент>_<тема>.md`; в `WAKE_QUEUE.md` — только актуальная «Текущая задача».
- Агенты, работающие параллельно, тоже обязаны фиксировать изменения по этому протоколу.

## Параллельная работа нескольких агентов (с 17.10.2026)
База рассчитана на одновременную работу нескольких агентов. Правила обязательны, нарушения — то же, что порча данных.

### 1. Реестр агентов
- При первой сессии добавь строку в `agents/REGISTRY.md` (имя, модель/среда, дата, скоуп).
- При последующих сессиях обновляй «Последняя сессия». Имя агента едино во всех файлах (REGISTRY, claims, LOG.md, отчёты).

### 2. Бронирование пазла (обязательно)
- Перед работой по пазлу: `python tools/claims.py acquire <slug> --agent <имя> [--ttl 120] [--note "скоуп"]`.
- Пазл забронирован другим и бронь не просрочена — **не трогай этот пазл** (ни код, ни LOG, ни README), возьми другой из очереди.
- Долгая работа: `heartbeat` раз в ~30 минут. По завершении: `release`. Просроченную бронь можно `steal` (факт — в LOG.md пазла).
- Скоуп (например «только балансы») указывай в `--note`; чужой скоуп уважай — не переписывай то, что он исследует.

### 3. Разграничение файлов (кто что пишет)
- `puzzles/<slug>/LOG.md`, `README.md`, `tools/`, `data/` — только агент, держащий бронь этого пазла.
- `reports/` — каждый агент пишет только СВОИ файлы (один проход = один файл).
- Общие файлы — `WAKE_QUEUE.md` («Текущая задача»), `puzzles/README.md`, `MASTER_CATALOG.md`, `solved/INDEX.md`:
  править атомарно (см. п.4), минимальным диффом, чужие строки не переставлять и не удалять.

### 4. Атомарные записи (OneDrive)
- Общие файлы не «пересохранять» долгими редакторами: цельная запись — temp-файл рядом + переименование поверх
  (PowerShell: `Set-Content tmp; Move-Item -Force tmp target`; Python: `os.replace`).
- Перед правкой общего файла перечитай его с диска — OneDrive мог принести чужие изменения; дифф строится от свежей версии.
- Конфликт-копии OneDrive (`...-DESKTOP-XXXX.md`, `... (Conflict ...).md`): найти, смержить содержимое, копию удалить, факт — в отчёт.
- Секреты (ключи/сиды) держать ВНЕ синхронизируемой папки, напр. `%USERPROFILE%\.secrets\master\<slug>\`
  (правило `.secret/` chmod 600 — для Unix; в OneDrive секретов быть не должно, только указатель).

### 5. Зона solved/
- `solved/` — решённые/закрытые/тупиковые пазлы (индекс: `solved/INDEX.md`). Активная работа там не ведётся.
- Новые данные (приз вернули/пополнили, автор открыл этап) → вернуть папку в `puzzles/<slug>/`, обновить оба индекса и LOG.

## GitHub-интейк — обязательный первый шлюз (с 18.10.2026)
Правило Ильи: «агент, который берёт базу в работу или отдельную загадку, сначала собирает на GitHub
всю информацию по ней из репозиториев». **Без пройденного шлюза нельзя выставлять строку в
`PROPOSALS.md` и нельзя запускать проверочный прогон.** Инструмент — `tools/github_intake.py`; он же
ведёт учёт общего часового лимита `api.github.com`.

### Когда
- Сразу после `claims.py acquire <slug>` и до любого предложения/прогона.
- Сессия «вся база»: идём через `backlog` — **одна цель за проход** (60 запросов/час — общий на IP всех агентов).
- Повторно, если шлюзу > 30 дней или изменился HEAD репо: `status <slug> --check-head`.

### Что собирается по цели
- репозитории самой загадки;
- репозитории автора и мейнтейнеров (хендлы берутся из досье и из записи OCP);
- сообщество: форки, issues, комментарии, pull requests, коммиты, release-ассеты, gists, wiki, метаданные;
- запись о пазле в `floflo777/open-crypto-puzzles` — офлайн из `_sources/ocp/puzzles.json` (0 запросов, повторных копий не делаем).
- Репо, у которых **нет github-ссылки в досье**, подхватываются бесплатно из следов других агентов: имена папок
  дампов `puzzles/<slug>/data/**/<owner>__<repo>` и ссылки в `reports/*<токен пазла>*.md` (прецедент 18.10:
  `testnetbtc/GSMG` и `AppleLamps/GSMG-CLEAN` нашли только отчётом соагента — `plan` по GSMG даёт 22 кандидата,
  с этим шагом 29). Если у пазла есть внешний скан-дамп в нестандартном пути, добавь его вручную: `run … --repo o/r`.

### Как (команды)
```bash
python tools/github_intake.py plan <slug> --no-net               # кандидаты + оценка затрат: 0 сети, ничего не пишет
python tools/github_intake.py run <slug> --agent <Имя> [--take-claim]   # сбор + дайдест + запись шлюза
python tools/github_intake.py status [<slug>] [--refresh]        # DONE|PARTIAL|NONE|STALE|LEGACY|PENDING
python tools/github_intake.py backlog --n 20 [--refresh]         # очередь целей для режима «вся база»
python tools/github_intake.py cache floflo777/open-crypto-puzzles  # общий кэш = git pull, 0 запросов
python tools/github_intake.py ledger [--reconcile]               # бюджет api.github.com (общий на IP)
python tools/github_intake.py gc-cache                          # чистка кэша API-страниц в _sources/github/_cache
```
- Содержимое реп качается **бесплатными** транспортами: `codeload`-тарболл по HEAD, фолбэк
  `git clone --depth 1 --single-branch` (вложенный `.git` удаляем). Ветку берём из
  `git ls-remote --symref` — у старых репо это `master`, угадывать нельзя.
- Квоту тратят только issues/comments/PR/releases/commits/gists/forks/search; ответ `304` по ETag = 0 запросов.
- Потолки прогона: **13 минут и 40 запросов** (под правило «прогон не дольше 15 минут»), пауза 1,2 с,
  запас 5 запросов до конца окна.
- Идемпотентность: непустой `files/` при том же HEAD не перекачивается; HEAD изменился → новый
  `files__<sha8>/`, старое не трётся. Уже лежащие дампы (GSMG `data/puzzlehunt/`,
  9vw04 `data/external/github/`) помечены в скрипте как легаси и не перекачиваются.

### Куда пишется
- `puzzles/<slug>/data/github/<owner__repo>/` — `files/` (снимок репо), `raw/` (issues/comments/… JSON),
  `media_index.md`, `REPO_META.json`;
- `puzzles/<slug>/data/github/GITHUB_INTAKE.md` — дайдест: таблица репо, индекс issues, выжимки комментов
  с проверяемыми константами (адреса/hex/формулы), «новое против досье», медиа-индекс, внешние ссылки и
  **обязательный раздел негативов и пропусков**;
- маркер `- GitHub-интейк: …` в `puzzles/<slug>/README.md`, запись в `LOG.md`, строка в
  `_sources/GITHUB_INTAKE_STATUS.md`.
- **Сырые дампы чужих репозиториев в git не коммитим** (`.gitignore`): в публичном репозитории остаются
  только наши выжимки (`GITHUB_INTAKE.md`, `REPO_META.json`).

### Негатив — тоже выполнение шлюза
Если репозиториев по цели нет, `run` пишет «репо не найдено, проверено по N запросам» и возвращает код `2` —
шлюз закрыт корректно, дальше можно предлагать и решать. У целей без GitHub-ссылок (таких большинство)
это типичный исход стоимостью ~0 запросов — поэтому шлюз не замораживает базу.

### Коды возврата `run`
`0` done · `1` отказ (чужая бронь / нет аргументов) · `2` none (негатив зафиксирован) ·
`3` partial (бюджет или дедлайн: остаток в `data/github/resume.json`, продолжить следующим прогоном).

### Шаблон записи в `puzzles/<slug>/LOG.md`
```
## YYYY-MM-DD, HH:MM — <агент> (<модель/среда>)
- GITHUB INTAKE (шлюз): run <slug> --agent <Имя> → статус done|partial|none, репо N, API M, файлов K.
- Собрано: <owner/repo — issues/comments/releases/…>, дампы в data/github/<owner__repo>/.
- Новое против досье: <ссылки/адреса/hex из дампа, которых не было в README/LOG> — или «нет».
- Негативы/пропуски: <что не собрано и почему>.
- Артефакты: data/github/GITHUB_INTAKE.md · реестр _sources/GITHUB_INTAKE_STATUS.md
```

## Стандартный цикл агента (с 17.10.2026): выбор цели → предложение → авто-решение → обогащение
Каждый новый агент работает этим циклом. Режимы: ВЫБОР ЦЕЛИ → ПРЕДЛОЖЕНИЕ → АВТО-РЕШЕНИЕ → (исчерпание попыток) → ОБОГАЩЕНИЕ → снова.

### 1. Выбор цели
- Источники кандидатов: `QUICK_WINS_2026-10-17.md` (ранжирование), Часть 1 каталога категория А (близкие к решению), «Текущая задача» в `WAKE_QUEUE.md`.
- Фильтры (все обязательны): пазл лежит в `puzzles/` (не в `solved/`); отсутствует в `dead-ends-registry`; **баланс жив** (проверить через blockchain.info/эксплорер непосредственно перед предложением); бронь свободна (`claims.py status <slug>`); задача соответствует ресурсам агента (без GPU не брать чисто-переборные оси).
- Критерий перспективы (по убыванию): известен механизм/оракул и остался один шаг до проверки → есть инсайт-угол (идея, сужающая пространство до ≤10⁴) → размер приза → свежесть подсказок автора.
- **Шлюз №0:** как только цель выбрана и забронирована — GitHub-интейк (`tools/github_intake.py run <slug> --agent <Имя>`); статус `DONE/PARTIAL/NONE/LEGACY` открывает путь к предложению, `PENDING`/`STALE` — нет.

### 2. Предложение пользователю (НЕ блокирует работу)
- Строка в `master/PROPOSALS.md` (атомарный append: перечитать файл → дописать строку → temp+rename) + подробный файл `reports/..._PROPOSAL_<slug>.md` (почему перспективна, план, риски, стоимость).
- Через **60 минут** после предложения агент начинает авто-решение, ЕСЛИ в таблице PROPOSALS не стоит вето. Пометка «одобрено» пользователем — начинать немедленно.
- Траты, транзакции, письма авторам — как и раньше, ТОЛЬКО с ОК Ильи (см. «Оперативные правила приоритета», п.5). Предложение != разрешение тратить.
- В начале ячейки «Статус» строки предложения — метка шлюза: `GH:done(3 репо, 27 req)` или `GH:none(3 req)` (см. раздел «GitHub-интейк»). Без метки предложение не считается выставленным.

### 3. Авто-решение с отчётами
- Бронь → работа циклами → каждый цикл: отчёт в `reports/`, значимое в `LOG.md` пазла.
- Перебор — на GPU или CPU, ≤15 минут на прогон, и ТОЛЬКО по оси, суженной инсайтом (гипотеза и ось — в LOG.md до прогона). Слепой перебор запрещён. Пользователю — краткий статус каждые N циклов строкой в отчёте.
- Перед первым прогоном цикла проверить свежесть шлюза: `python tools/github_intake.py status <slug>`; `PENDING`/`STALE`/`PARTIAL` — сначала довести интейк (или зафиксировать негатив), потом перебирать.

### 4. Исчерпание попыток → режим ОБОГАЩЕНИЯ
- Если 3 цикла подряд по одному пазлу не дали ни одной новой проверенной информации (включая отрицательные результаты по НОВОЙ оси) — попытки исчерпаны: пометить статус предложения «исчерпано», зафиксировать закрытую ось в `LOG.md`, отпустить бронь.
- Переключиться в ОБОГАЩЕНИЕ: методично наполнять папки пазлов из сети (начать со скелетных README из `BASE_AUDIT_2026-10-17.md`, далее по индексу): первоисточники, подсказки автора, комментарии решателей, архивные версии страниц, машинные данные — файлы в `data/`, выжимка в `README.md`, ВСЁ с URL и датой; негативы — тоже в LOG. Обогащение — это сбор и анализ; проверочные прогоны допустимы только по оси, суженной найденным инсайтом (≤15 мин/прогон).
- Найден инсайт/новая зацепка по любому пазлу → вернуться в режим решения (предложение + авто-решение).
- **GitHub-интейк — первый шаг обогащения** по цели: если он ещё не пройден, начинать именно с него (`run <slug>`), затем `backlog` по соседним пазлам.

### 5. Постоянные обязанности (в любом режиме)
- Новые загадки из сети/реестров → папка `puzzles/<slug>/` + индекс + каталог.
- Параллельный протокол (брони, реестр агентов, атомарность, отчёты) — обязателен всегда.
- Поддерживать реестр шлюза: `_sources/GITHUB_INTAKE_STATUS.md` (`status --refresh`) и очередь `_sources/github/INTAKE_BACKLOG.md` (`backlog --refresh`); общий кэш — `_sources/github/` (не дублировать репо в папках пазлов, `cache <owner/repo>`).
