## 3. Поиск готовых решений (приоритет №1)

### Методика
`tools/harvest_published_keys_v2_2026-10-19.py` (исправлен баг v1: v1 молча пропускал **сжатые**
WIF `K…/L…` — теперь оба варианта). Источники:
1. локальное дерево `master/` (2445 `.md`, включая `_sources/` и data/);
2. OCP-снимок `ocp_puzzles.json` (49 пазлов);

Для каждого найденного ключа/WIF/сид-фразы деривятся адреса (P2PKH unc/cmp, P2WPKH,
P2SH-P2WPKH; BIP44/49/84/Electrum; первые 3 индекса) → 13 876 уникальных адресов-кандидатов.

→ Ни один опубликованный ключ в корпусе не контролирует адрес с деньгами.

## 4. Вывод
**Готовых опубликованных решений, контролирующих живые балансы, в корпусе (локальное дерево +
OCP-снимок) не найдено.** Извлечение балансов «одним кликом» невозможно — нужны либо новые
публикации, либо криптографическое решение пазлов (GSMG, 1000-BTC, bitaps-shamir, ballet,
AoI и т. д.), что вне рамок harvest-прохода.

## 5. Кошелёк песочницы (блокер)
В репозитории **нет** кошелька/адреса песочницы: нет `.secret/`, нет ключей/адресов назначения.
С sweep-транзакциями — только с явным ОК Ильи. **Нужен от Ильи:** destination-адрес (и, при
необходимости, способ подписи) для приёма выметённых балансов.

## 6. Следующие шаги
1. Дождаться завершения фонового sweep; если появятся hits — немедленно вынести ключи в
   `.secret/` (не в отчёты/каталог) и запросить ОК на sweep.
2. Решить судьбу onfo/thune (см. §2) — оставить в `solved/` или вернуть в `puzzles/`.
3. Обогащение папок из сети (скелетные README из BASE_AUDIT) по протоколу 3 цикла без новой
   проверенной информации → переключение в enrichment-режим.
4. При появлении новых данных по Vault #2 (1 BTC, «Postponed until further notice», ноль хинтов)
   — приоритетная цель, т. к. самый свежий живой эскроу с неизвестным ключом.
