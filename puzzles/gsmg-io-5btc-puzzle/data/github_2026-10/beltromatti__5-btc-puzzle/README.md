# GSMG 5 BTC Puzzle

This repository collects one exploratory branch I followed while working on the old GSMG 5 BTC puzzle.

For me, this ended up being a pretty good example of what a state-of-the-art AI model can actually do today in practice: help you enter a completely new domain fast, study it much more efficiently, write code quickly, and speed up research enough to produce something genuinely interesting and useful.

At the same time, this also made one thing very clear to me: the model does not replace the person doing the work. You still need someone keeping the big picture in mind, applying critical thinking, deciding what is noise and what is worth pushing further, and having the intuitions that give the search a direction. In my case, GPT-5.4 was an incredibly strong research and coding assistant, but the overall vision and the decisions about where to go next were still mine.

I’m Mattia Beltrami, 21, a computer engineering student at Politecnico di Milano, and I’m sharing this branch because even without a final solution it feels reproducible and potentially useful to others.

## Starting point

I started from the currently public/reproducible state that leads from Cosmic Duality to the final **68-byte** output.

The standard interpretation I kept seeing was basically:

- first 32 bytes = Half
- next 32 bytes = Better Half
- last 4 bytes = trailing marker

I tried a different interpretation that felt more structurally meaningful:

- first 64 bytes = **4 blocks of 16 bytes**
- last 4 bytes = **4 x-coordinates**

So the 68 bytes become:

- `E(fc) = 0423d9115a1dc756d5d08d2de880ab50`
- `E(0c) = 8bd4745fc97709f4fcb513f2cb8fcc35`
- `E(1b) = 48cc46e66bdd36b09ae344552f606a76`
- `E(02) = 1f9d90681f20dfefe2b43db18b623971`

and the last 4 bytes are interpreted as the x values:

- `fc, 0c, 1b, 02`

## What I tried

I treated those 4 blocks as values of a cubic polynomial, **byte by byte**, over **GF(256)**.

So for each byte position `j = 0..15`, I interpolate a cubic polynomial `p_j(x)` such that:

- `p_j(fc)`
- `p_j(0c)`
- `p_j(1b)`
- `p_j(02)`

match the observed 4 blocks.

Then I define:

- `E(x) = p_0(x) || p_1(x) || ... || p_15(x)`

This gives some very clean extra evaluations, especially:

- `E(00) = 5b53b1be263aacaa4f70e3b7b3a4a2e9`
- `E(04) = 15b331f311c05c4b2895f9f9d47474d8`
- `E(0f) = 613056fbcd1510dde6de488994081aa3`

So the natural 7-point set becomes:

- `fc, 00, 02, 04, 0c, 0f, 1b`

At that point I built XOR triangles from these 7 blocks and started scanning them.

## What I checked so far

### 1) Two 16-byte blocks concatenated into a 32-byte private key

I tested all ordered pairs `E(a) || E(b)` from the full GF(256) model.

No exact match for the target P2PKH address.

### 2) XOR / subset-xor combinations

I tested XOR-closed families generated by the 7-point set, including the usual “triangle” nodes and subset-xor candidates.

Again, no exact match.

### 3) Full triangle level scans

This is where it got more interesting.

For the 7-point set above, I tested **all 2520 unique permutations modulo reversal**.

For each permutation I built the XOR triangle and tested:

- every level `level_0 ... level_6`
- `sha256(level)`
- `double-sha256(level)`

Each digest was then checked as a secp256k1 private key against the target address, both as:

- compressed pubkey
- uncompressed pubkey

Still **no exact match**.

## Current best near-miss

The best result I found so far is:

- order: `00, 0f, 0c, fc, 02, 04, 1b`
- triangle row: `level_3`
- transform: `double-sha256(level_3)`
- best format: **uncompressed**

Resulting hash160:

- `a955a042e800556fdeea1eb9cc0b80a196cf76a5`

Target hash160:

- `a9553269572a317e39f0f518cb87c1a0ee1dbae4`

So it shares the prefix:

- `a955`

I know 4 hex chars are **not proof of anything**, but in my scans this was not just random noise spread everywhere. It came out as the strongest signal inside that whole family.

For reference, in that same scan family I only got a handful of `a95...` cases, and this was the only one reaching `a955...`.

## Extra note

I also tried local modifications around that hot case:

- permutations of the 4 blocks inside `level_3`
- byte reversals
- full reversal
- small pairwise foldings / XOR foldings
- combinations with neighboring levels

None of those gave an exact hit, and none improved the `a955...` near-miss.

So at least from my tests, if this model is on the right track, the final step probably is **not** just:

- “pick two 16-byte pieces and concatenate them”
- or “slightly reorder the middle row”

It feels more like a **global serialization problem** on the triangle, or some other final mapping that preserves structure.

## Why I’m posting this

I’m posting this mainly because:

1. this gives a different and fairly simple interpretation of the final 68 bytes (`4 x 16 + 4 x-values`)
2. it produces a reproducible 7-point structure
3. it lets you scan a big family of triangle-based constructions without going completely blind
4. even though I did not solve it, this line produced the best near-miss I’ve seen in my own tests

If anyone thinks this model is nonsense, that’s also useful feedback.  
If anyone sees why the order `00,0f,0c,fc,02,04,1b` or the middle row `level_3` might actually be meaningful, I’d really like to hear it.

This repo includes the scripts needed to reproduce the GF(256) interpolation, triangle construction, full level scan, and hot-case reconstruction.

## Reproducing

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 scripts/gf256_interp.py
python3 scripts/reproduce_hot_case.py
python3 scripts/scan_levels.py
```
