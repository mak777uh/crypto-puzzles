## `guntis-vitolins-metamask-8-6eth` — findings + errors that stayed inherited

Working through this puzzle intensively this session. Sharing what turned up so future solvers don't inherit the same errors we did. Full notes in a longer local doc; this issue is the summary.

### Errors in the current write-up (`analysis/tested.md` + `README.md`)

1. **`top`** — cited to *"video title and hook line"*. Case-insensitive grep of the 2020-06-13 Wayback capture of `youtube.com/watch?v=w4mpiuBP_aY` returned zero hits in title or `og:description`. `top` does appear in the wider blog body prose (*"top ten altcoins"*) and in the video description trailer (*"top mining equipment"*), so the word might still be a candidate — but the sourcing statement is wrong. This propagated into `R1` and every downstream sweep.
2. **`finish`** — placed in the R1 pool as a title/hook-line word. `finish` (bare stem) does not appear literally in any authored surface. `finished` (past participle) is in the og:description tagline *"Crypto Winter finished?"*. So `finish` is a morphological derivative (same class as the F6 inflection sweep), not a literal.
3. **`cloud`** — the README explicitly says *"only `fog` and `lake` appear in the source texts"*, then still carries `cloud` as a pos-5 branch on semantic-fit grounds. Direct grep of every 2020 authored surface (blog HTML, main video HTML, main video description) confirms zero authored `cloud` occurrences — the only hits anywhere are modern (post-2023) CDN URLs and YouTube player JS variables. Every sweep with a `cloud` branch doubled compute on a candidate that fails the "correct word in text at challenge" rule Guntis stated in the Hint-5 video comments.
4. **`fork`-absence-treated-as-elimination** — earlier phases OCR'd 216 images to search for `fork`; found none; the null was interpreted as ruling `fork` out. The tag list in blog HTML metadata had it all along (`ethereum fork` tag, unique-to-this-post). Discovered 2026-08-15 per the repo's own timeline.

### Unresolved contradiction not to close

`analysis/leads.md` cites Guntis's own *"'possible' inside 'impossible' via 'im-' prefix"* example as evidence for a substring mechanism. That contradicts the literal-word rule the same source uses elsewhere. Substring families in the repo's own leads (Tier B, Tier C-length candidates) were never swept exhaustively; this session ran substring Tier A (6 candidates including `possible`) and then deprioritized on a judgment call in favor of the literal rule. If the substring mechanism is real, every literal-rule sweep is over-constrained.

From `-MeIaPdVJjA` (comment id `Ugz8NxQbpGiZVY4aMlB4AaABAg.96ssUYBoRva96tAygBNjKq`, 2020-08), replying to a question about pool size:
